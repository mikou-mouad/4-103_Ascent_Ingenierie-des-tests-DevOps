Chapitre 7 · Le concept

Vérifier la production, et revenir en arrière tout seul

try {
    sh 'bash deploy/deployer.sh prod $VERSION'
    sh 'bash deploy/smoke-test.sh http://embarq-prod:8080 $VERSION'
} catch (erreur) {
    if (precedente) { // la version qui tournait avant
        sh "bash deploy/deployer.sh prod ${precedente}"
        sh "bash deploy/smoke-test.sh http://embarq-prod:8080 ${precedente}"
    }
    error "Mise en production de ${env.VERSION} annulée. …"
}

Smoke tests

Santé UP, la bonne version, l'accueil, l'API, un tarif connu : 90 € pour 2 adultes et 1 enfant.

Blue/green

Deux productions, on bascule de l'une à l'autre.

Canary

La nouvelle version pour une petite part du trafic d'abord.

Feature flags

Le code est livré, la fonction s'allume plus tard.

Extrait de l'étape Production du Jenkinsfile final : la version précédente est lue avec docker inspect sur embarq-prod-app-1 avant le déploiement. smoke-test.sh vérifie /actuator/health, puis la version dans /actuator/info : c'est ce contrôle qui aurait évité « une version que personne ne savait nommer ». Blue/green, canary et feature flags ne sont pas mis en œuvre dans le lab : ce sont des réponses possibles à la question de fin 2 du TP 07.
