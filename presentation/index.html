Chapitre 0 · Le concept

CI, livraison continue, déploiement continu

Intégration continue

Chaque push est compilé et testé. Un problème est vu en minutes, pas en jours.

Livraison continue

Chaque version est prête à partir. La mise en production reste une décision humaine : un bouton.

Déploiement continu

Tout ce qui passe le pipeline part en production, sans intervention.

Infrastructure as code

Le lab, Jenkins et le pipeline sont des fichiers versionnés.

lab/docker-compose.yml
lab/jenkins/casc.yaml
embarq/Jenkinsfile

CE QUE DEVOPS CHANGE POUR LES TESTS

Ils tournent à chaque changement, pas avant la livraison.

Ils doivent être rapides, fiables, automatiques.

Leur résultat est visible par tous.

Ils deviennent la porte de la production.

Question pour la salle : où en est Embarq aujourd'hui ? Nulle part : ni CI, ni livraison. À la fin du TP 07, Embarq sera en livraison continue (approbation humaine avant la production) ; passer au déploiement continu, c'est retirer le bouton. Infrastructure as code : au TP 00, personne ne clique pour créer le job Jenkins ni installer ses plugins (casc.yaml, plugins.txt).

GitLab reste la porte d'entrée, comme dans l'environnement réel des participants ; Jenkins fait le travail. ReservationRepository

@DataJpaTest
@Testcontainers
class ReservationRepositoryIT {

    @Container
    @ServiceConnection
    static PostgreSQLContainer postgres =
        new PostgreSQLContainer("postgres:17-alpine");

    // placesReservees() interrogé pour de vrai
}

@DataJpaTest démarre seulement la couche base de données de Spring (entités, dépôts, Flyway). @Testcontainers et @Container démarrent PostgreSQL 17 dans Docker pour la durée des tests. @ServiceConnection branche Spring sur ce conteneur, sans configuration. Les tests *IT sont lancés par failsafe à l'étape verify, après les tests unitaires. Pourquoi pas H2 en mémoire ? Ce n'est pas la base de production : une requête peut s'y comporter autrement. Dans le vrai fichier, il y a aussi @AutoConfigureTestDatabase(replace = NONE).

Chapitre 2 · Le concept

Tester la charge : l'ouverture du 1er avril

// perf/charge.js (k6)
export const options = {
  stages: [
    { duration: '20s', target: 20 }, // montée
    { duration: '30s', target: 20 }, // plateau
    { duration: '10s', target: 0 }, // descente
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
  },
};

Montée en charge

Des visiteurs virtuels arrivent peu à peu, restent, repartent. Chacun consulte les traversées et calcule un prix.

Des seuils, pas des impressions

95 % des réponses en moins de 500 ms, moins de 1 % d'erreurs. Sinon, k6 sort en erreur.

Sur le bon environnement

Le résultat dépend de la machine : un test sur votre poste ne prouve pas que la production tiendra.

k6 tourne dans un conteneur, sur le réseau du lab : docker run --rm -i --network lab grafana/k6:1.8.2 run -e BASE_URL=http://embarq-dev:8080 - < perf/charge.js. p(95) : le temps sous lequel passent 95 % des requêtes ; une moyenne cache les lentes. Question 6 du TP 02 : simuler 300 visiteurs, et choisir quand et où lancer ce test (pas forcément à chaque push).

Chapitre 3 · Le concept

La qualité dès le début, et l'affaire de tous

LA QUALITÉ À LA FIN

  • Tom code, puis passe la main.
  • Inès teste deux jours, juste avant la livraison.
  • Un défaut trouvé tard bloque tout.
  • Chacun défend son étape.

LA QUALITÉ DÈS LE DÉBUT

  • Les exemples sont écrits avant le code.
  • Les tests font partie du code, revus comme lui.
  • Un test rouge arrête la chaîne : on le répare.
  • Les chiffres sont visibles par tous.

Dev, test, ops : un seul pipeline, un seul verdict, une responsabilité partagée.

La culture du test ne s'achète pas avec un outil. Questions pour la salle : chez vous, qui écrit les tests ? Qui les répare quand ils cassent ? Qui décide qu'une version peut partir ? Un pipeline rouge que personne ne regarde n'est pas une culture qualité. Les exemples écrits avant le code reviennent au chapitre 4 (les trois amigos).

Chapitre 3 · Le concept

Des chiffres qui aident à décider

La couverture

Le code exécuté par les tests. Pas la justesse des vérifications : 100 % de couverture n'empêche pas un bug.

Les tests instables

Vert « presque toujours » : un signal qu'on apprend à ignorer. On le corrige, on ne le relance pas.

La quality gate, en cliquet

Le seuil JaCoCo est fixé au niveau actuel, puis remonté à chaque nouveau test : la couverture ne baisse plus.

Fréquence de déploiement · délai de mise en production · taux d'échec des changements · temps de rétablissement.

Chapitre 4 · Le concept

Gherkin : des règles qu'on exécute, en français

# language: fr
Fonctionnalité: Prix d'une traversée

  Règle: Tarif résident des îles

    Contexte:
      Étant donné des passagers résidents des îles

    Scénario: Un adulte résident paie 9 €
      Quand je réserve pour 1 adulte, 0 enfant et 0 vélo
      Alors le prix est de 9,00 €

Étant donné le contexte, Quand l'action, Alors le résultat attendu.

Chaque phrase est reliée à une méthode Java par une expression Cucumber :

@Quand("je réserve pour
 {int} adulte(s), {int} enfant(s)
 et {int} vélo(s)")

Maëlle lit le scénario. La machine le vérifie.

Extrait réel de embarq/src/test/resources/features/tarifs.feature. Le fichier du TP contient aussi la règle du tarif normal, en Plan du scénario avec un tableau d'Exemples. Dans TarifsSteps : {int} capture un nombre, {bigdecimal} un montant avec une virgule (le fichier est en français), adulte(s) accepte le singulier et le pluriel. Si Cucumber écrit « The step … is undefined », la phrase ne correspond à aucune expression : comparer mot à mot.

Chapitre 5 · Le concept

Page Object et attentes explicites

// PageReservation : une classe par page
PageReservation(WebDriver navigateur) {
    this.navigateur = navigateur;
    new WebDriverWait(navigateur, Duration.ofSeconds(10))
        .until(ExpectedConditions
            .visibilityOfElementLocated(By.id("valider")));
}

public PageConfirmation valider() {
    navigateur.findElement(By.id("valider")).click();
    return new PageConfirmation(navigateur);
}

La page connaît les sélecteurs et offre des actions métier.

Le test ne contient aucun sélecteur :

PageAccueil.ouvrir(navigateur, APP_URL)
 .reserverLaPremiereTraversee()
 .saisir("Le Gall", …, 2, 1, 0)
 .valider();

On attend un état, pas une durée. Jamais de Thread.sleep.

Extrait de la correction du TP 05 (solutions/05-selenium/). Au TP 06, les By.id deviendront testId(…) : seules les trois pages changeront, pas ReservationE2E. Pourquoi pas Thread.sleep(2000) ? Trop court sur une machine chargée (test instable), trop long le reste du temps (pipeline lent). L'attente explicite rend la main dès que l'élément est là, et échoue clairement après 10 secondes.
